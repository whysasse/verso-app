# FAB-334 — Verso 1.1 "native iOS shell" implementation plan

**Version:** 1.1 · **Date:** 2026-09-12 · **Status:** Active

> **2026-09-12 correction:** Decision #2 below is superseded — Fabio chose to
> fold this into 1.0 and build it before the App Store launch, not after.
> See the corrected row in §1 and the reworded §1.1/Phase 1. Nothing else in
> this document changes.

**Parent issue:** [FAB-334](../BACKLOG.md) — [Epic] Native iOS shell: replace custom chrome with system components (Liquid Glass)
**Goal:** The article list, settings, search, navigation and toolbars become system components and adopt Liquid Glass automatically. The reading view is not touched.
**Done when:** `VersoNavigationBar`, `SearchBar`, `SettingsRow`, `ThemeSelector`, `headerRow` and `FilterPanel` are gone; Settings is a `Form`; the list is a system `List` with `EditMode`; search is `.searchable`; the full screenshot matrix passes on device, and a first-run user lands in the reading view with a
welcome article rather than on an empty list.

---

## 0. What this plan adds to the epic

The epic ([BACKLOG.md](../BACKLOG.md), Phase E) was written 2026-09-03, before the whole Phase D chain shipped and before iOS 27's release date was known. Its reasoning holds. Its *numbers* have drifted, and a code audit on 2026-09-08 surfaced four architectural risks it doesn't name. This document is the executable version: re-measured, decisions closed, phases ordered, risks named.

Read the epic for **why**. Read this for **what to do**.

## 3. Risks the epic doesn't name

These four came out of the audit. Each one can stall a phase if it's discovered mid-implementation instead of before.

### R1 ✅ `EditMode` collides with the split-view selection binding — resolved, option (b)

`ArticleListView.swift:452`:

```swift
List(selection: isSelecting ? .constant(nil) : $selectedArticle) {
```

That single-value `Article?` binding is not decorative — it is the mechanism `NavigationSplitView` uses to drive sidebar→detail push on iPhone. `VersoMainSplitView.swift:9–13` documents why (`NavigationLink(value:)` in the sidebar cannot see a `.navigationDestination(for:)` in the detail column, so `List(selection:)` is doing the collapse).

`EditMode` multi-select requires `List(selection: Binding<Set<ID>>)`. A `List` takes **one** selection binding. So phase 6 cannot just "adopt `EditMode`". Two options, decide before starting:

- **(a)** Swap the binding on edit-mode change. Changes the `List`'s generic type, which rebuilds it — scroll position and section collapse state are lost entering and leaving select mode. A visible regression against today's behaviour.
- **(b)** Keep the bespoke `selectedArticleIds: Set<UUID>` and borrow only `EditMode`'s *chrome* (the `.toolbar` Edit/Done button, the "N Selected" title, `Button(role: .destructive)` rendering red now that `.buttonStyle(.plain)` is gone). Delivers everything FAB-320 asks for without touching the collapse mechanism.

**DECIDED 2026-09-08 (Fabio): option (b).** FAB-320's actual complaints are "delete isn't red" and "nothing
shows a count" — neither needs the system's selection machinery, only its styling and its title convention.
Trading a working navigation collapse and the user's scroll position for an idiomatic selection binding is a
bad trade, and the parallel `Set<UUID>` is invisible state rather than the re-implemented *chrome* this epic
exists to delete.

**What (b) means concretely in phase 6** — the selection model does not change at all:

| Keep as-is | Change |
|---|---|
| `selectedArticleIds: Set<UUID>` | Drop `.buttonStyle(.plain)` from the two bulk-action buttons → `Button(role: .destructive)` renders red, for free (this *is* FAB-320's first half) |
| `List(selection: isSelecting ? .constant(nil) : $selectedArticle)` — untouched, so the split-view collapse keeps working | Move both actions out of the hand-built `safeAreaInset` bar into the real `.toolbar` phase 4 provides |
| The per-row `Button` that toggles membership | "N Selected" as the navigation title; Cancel/Done as toolbar items (FAB-320's second half) |
| | Draw a system checkmark in the row Button |

**Accepted losses:** no free Select All, no drag-to-select-multiple, and the row checkbox stays hand-drawn.
None were asked for; open a ticket if they're wanted later.

*Optional, non-blocking:* if there's a spare half-hour in phase 6, it's still worth observing whether swapping
the binding actually breaks `List` identity (scroll position + section collapse, from a deep scroll). The claim
is reasoned from SwiftUI's type system, not measured. It changes nothing about this decision — it would only
tell us how much option (a) would have cost. **Do not gate phase 6 on it.**

### R2 🟠 `.id(listFetchIdentity)` rebuilds the whole list on every keystroke

`ArticleListView.swift:126` keys the fetched body on a signature that includes `searchText`. Today the custom `SearchBar` is deliberately placed *outside* that subtree — the comment at line 100 says so: *"Outside `.id(listFetchIdentity)` so typing doesn't recreate this view and drop keyboard focus."*

`.searchable` puts the field in the navigation or bottom bar, also outside the subtree, so **focus is safe**. What isn't safe is that every keystroke still tears down and rebuilds the entire fetched body — and iOS 26's search field animates its own transition on top of that. Expect visible jank that the current design hides.

**Fix before phase 5:** debounce `searchText` into the predicate (~250ms), or drop the `.id()` in favour of mutating the `@FetchRequest` predicate in place. The second is cleaner and removes a re-keying hazard that already caused one 1.0 bug (see R3).

### R3 🔴 Phase 4 is FAB-304 territory, literally

`ArticleListView.swift:168–186` carries the two things that made FAB-304 cause 1 hard: `.toolbar(.hidden, for: .navigationBar)`, and a long comment explaining why `.navigationDestination(isPresented: $showSettings)` must be attached to the **stable ancestor** rather than inside the `.id()`-keyed body — otherwise a theme flip re-keys the subtree, the destination disappears while `showSettings` stays `true`, and the user gets a blank pushed screen.

Phase 4 removes that hidden toolbar and moves Settings into a real toolbar item. **The anchoring constraint has to survive the move.** Add a regression check to the phase's verification: push Settings, background the app, switch theme across the light/dark boundary, return — the screen must still render.

**Confirmed live 2026-09-12, and narrower than assumed.** Fabio hit a blank screen changing themes from phase 3's new `ThemePickerView` (`SettingsView` → `NavigationLink` → `ThemePickerView`, a **second** push level that didn't exist pre-phase-3 — the old `SettingsView` changed themes inline via `ThemeSelector`, no extra push at all). FAB-304's original fix only ever protected `showSettings`'s own presentation, one push deep off `ArticleListView`'s stable ancestor — it was never exercised against a *second* push level, because one didn't exist until phase 3 added it. Fixed by reverting to the inline pattern (exactly `ThemeSelector`'s old layout, now inside `SettingsView`'s `Form`) rather than debugging the deeper NavigationStack/hosting interaction blind.

**The general lesson, not just this one instance:** every phase that adds *new* navigation depth (a push that didn't exist before) is untested exposure to this rebuild, regardless of whether it's "inside" or "past" the point R3's original fix covers. Don't assume a new push is safe by analogy to `showSettings`'s fix — each new depth needs its own on-device theme-crossing check before it ships. Phase 4 itself doesn't add push depth (Settings is still one level off the list, same as before), so its own R3 check above still stands as originally scoped — but phase 6 (bulk-select chrome) and phase 7 (button sweep) should each ask this question explicitly rather than inherit a false sense of safety from R3 being "handled."

### R4 🟡 Theme flips force a hosting-hierarchy rebuild, under new chrome

`ContentView.swift:26` — `.preferredColorScheme(themeManager.currentTheme.isDark ? .dark : .light)`. Decision 3 means the shell follows this correctly by construction, which is good. But the reader still switches among four themes, two of which cross the light/dark boundary, and each crossing rebuilds the hierarchy *underneath* live Liquid Glass chrome. Nobody has seen that transition. Cover it in the spike.

## 4. Phases

Every phase builds, runs and ships on its own. No long-lived branch.

### Phase 0 — Material spike (throwaway, ~1 day) — ✅ done 2026-09-12, verdict: proceed

The epic's own caveat, restated because it gates phases 4–7: the direction was approved from an **HTML mock** using `backdrop-filter`. That's a colour-and-legibility approximation with no specular edge, no rim refraction, no scroll or tilt response — exactly the properties that could misbehave over a warm cream ground.

- One throwaway branch, one screen, real `glassEffect`, **on device**, all four themes.
- Answer: does real Liquid Glass dull Paper and Sepia in a way the mock didn't predict?
- Also exercise **R4** — flip Paper→Night with glass chrome on screen.
- **Fallback if it fails:** opaque chrome in the light themes, glass in the dark ones. Worth knowing now, not with the shell half-rebuilt.
- Delete the branch. Nothing from the spike merges.

**Gate: phases 4–7 do not start until the spike passes.** Phases 1–3 are safe either way.

#### Verdict (Fabio, on-device, 2026-09-12)

First pass (plain `.glassEffect(.regular, ...)`, hand-colored icons via `.foregroundColor(accent)`, no `.preferredColorScheme`) found two problems: untinted glass reads as flat neutral gray over Paper/Sepia — genuinely dulls the warmth, confirming the epic's worry — and icons were **illegible on Night/Ink**, invisible against the glass pill. That second one turned out to be a spike bug, not a material limitation: the icons were hand-tinted with no system vibrancy to lean on, unlike a real system-styled control.

Fixed and re-tested: real system `Button`s (not `.buttonStyle(.plain)` + manual `.foregroundColor`) plus `.preferredColorScheme(theme.isDark ? .dark : .light)` made icons legible in all four themes. Comparing tinted glass (`Glass.regular.tint(colors.accent.opacity(0.35))`) against untinted side by side, tinted clearly keeps more of each theme's character — most visible on Sepia, where untinted reads pale/washed and tinted reads warm tan. Fabio's call: **"a lot better now"** — proceeds.

**Two concrete requirements this carries into phases 4–7, not just a general green light:**

1. **Tint every `glassEffect` with the active theme's accent** (`Glass.regular.tint(colors.accent.opacity(~0.35))`, tune per surface) — plain `.regular` is the one combination confirmed to wash out Paper/Sepia. Don't ship untinted glass over the reading themes.
2. **Retire hand-colored icon buttons in favor of real system `Button`s wherever they sit on glass.** This is also exactly what phase 4's `.buttonStyle(.plain)` sweep and the `VersoToolbarIconButton` split (see §2's correction) were already going to do — the spike confirms it's not just a style preference, it's what makes icon contrast work on dark glass at all.

No opaque-chrome fallback needed — tinted glass covers it.

### Phase 8 — Welcome article (FAB-338)

Seed a real Markdown article into the user's folder on first run, so the first thing they see is the reading view with content in it rather than an empty list. It carries the instructions, feature descriptions and usage tips that the deleted tour used to.

**Why this is the right shape.** Verso's entire pitch is *your articles are plain Markdown files you own*. A welcome article demonstrates that in the first ten seconds — the user can open their iCloud folder and find the file sitting there. It also teaches inside the real reading view against real content, instead of illustrating controls on a carousel. And it doubles as a first-run QA artifact: give it headings, lists, a blockquote, an image and a few hundred words, and it exercises `HighlightableRegionText`'s region splitting, scroll progress, and the reading-time estimate the moment the app opens.

**Why it comes last.** The tips describe the shell's controls. Writing them before phases 3–7 land means rewriting them. Draft the prose *during* the shell work; finalise control names and any screenshots at the end.

**Constraints — these are what make it acceptable rather than intrusive:**

1. **Written once, at folder-pick time**, never before (there is no folder to write to during Welcome). Guarded by its own flag, not onboarding's.
2. **Deleting it is permanent.** If the user removes the file, `ICloudFileWatcher`'s next rescan must not resurrect it. The flag has to survive the delete — this is the one implementation detail most likely to be got wrong.
3. **Never overwrite an existing file** of the same name, and never write into a folder that already contains `.md` files (`SettingsView.hasMarkdownFiles(in:)` already implements this check — reuse it). Someone pointing Verso at an existing Obsidian vault must not find a new file in it.
4. **Honest frontmatter.** No fabricated `source:` or publisher. It is not a saved article and should not pretend to be one; a fake source URL would also make it sort oddly and corrupt the library's own data model.
5. **Three locales.** EN-CA, FR-CA, PT-BR. This is real prose, not strings-file entries — budget genuine translation time, and accept that it goes stale as the UI changes. Keep it short enough that maintaining three copies is not a burden.

**Decided 2026-09-08 (Fabio): it stays.** No auto-archive after the first real save. Auto-archiving would be the app quietly touching the user's data a second time, and it contradicts the "these are just your files" pitch the article exists to demonstrate. The user archives or deletes it like any other article — and per constraint 2, deleting it is permanent.
