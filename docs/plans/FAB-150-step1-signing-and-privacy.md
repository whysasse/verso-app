There are three targets: `Verso` (app), `ShareExtension` (app-extension, embedded in the app), `VersoTests` (unit tests).

## Task 1 — Plumb `DEVELOPMENT_TEAM` through all three targets

### The bug

`project.yml` sets, on each of the three targets:

```yaml
DEVELOPMENT_TEAM: "$(DEVELOPMENT_TEAM)"
```

…but nothing ever defines `DEVELOPMENT_TEAM`. It isn't in `Secrets.xcconfig`, isn't in the template, isn't in the environment. Every build so far has resolved it to empty string.

Worse, this indirection can't work even once the value exists. Xcode's build-setting precedence is:

```
target settings  >  target xcconfig  >  project settings  >  project xcconfig
```

`settings.base` in `project.yml` becomes **target settings** — the highest level. A target-level `DEVELOPMENT_TEAM = $(DEVELOPMENT_TEAM)` self-reference is fragile and frequently resolves to empty rather than falling through to the xcconfig. The fix is to delete the target-level line entirely and let the xcconfig value flow up unopposed.

Also note: `Secrets.xcconfig` is currently attached **only to the `Verso` target**. `ShareExtension` and `VersoTests` have no `configFiles` at all, so they'd see nothing from it regardless.

### Edits

**1a. `Verso/Secrets.xcconfig.template`** — add the new key with an empty value and a comment. Keep the existing `TELEMETRY_DECK_APP_ID` line:

```
// Your Apple Developer Team ID. Find it at developer.apple.com → Membership details.
// Required for code signing; builds will fail to sign without it.
DEVELOPMENT_TEAM =
```

**1b. `Verso/Secrets.xcconfig`** (gitignored, local only) — add the real value:

```
DEVELOPMENT_TEAM = <Fabio's Team ID>
```

**The Team ID is deliberately not written down in this repo.** It lives only in the gitignored `Secrets.xcconfig`, consistent with how `TELEMETRY_DECK_APP_ID` is handled. Ask Fabio for the value, or read it from an existing local `Secrets.xcconfig` if one is already filled in. Do not commit it, and do not paste it into this plan, `Secrets.xcconfig.template`, `project.yml`, or a commit message.

If `Secrets.xcconfig` doesn't exist yet, run `./generate-xcodeproj.sh` once to bootstrap it from the template, then fill it in.

**1c. `Verso/project.yml`** — remove the `DEVELOPMENT_TEAM: "$(DEVELOPMENT_TEAM)"` line from `settings.base` on **all three** targets (`Verso`, `ShareExtension`, `VersoTests`).

**1d. `Verso/project.yml`** — add the config file to `ShareExtension` and `VersoTests` so they inherit the team. Paths are relative to the spec's directory (`Verso/`), matching the existing `Verso` target:

```yaml
    configFiles:
      Debug: Secrets.xcconfig
      Release: Secrets.xcconfig
```

**1e. `Verso/generate-xcodeproj.sh`** — the script bootstraps `Secrets.xcconfig` from the template only when the file is *absent*. Anyone with an existing pre-change `Secrets.xcconfig` will silently keep a file with no `DEVELOPMENT_TEAM`. Add a check after the bootstrap block that greps the file for `DEVELOPMENT_TEAM` and prints a clear warning (not a hard failure — CI and contributors without a paid account should still be able to generate).

### Also fix: `CODE_SIGN_IDENTITY` blocks distribution builds

All three targets hardcode:

```yaml
CODE_SIGN_IDENTITY: Apple Development
```

alongside `CODE_SIGN_STYLE: Automatic`. This is fine for running on a device, but it **will break the Release archive** — an App Store archive needs an `Apple Distribution` identity, and pinning `Apple Development` produces either a provisioning-profile mismatch at archive time or a dev-signed archive that App Store Connect rejects on upload.

**Remove the `CODE_SIGN_IDENTITY` line from all three targets.** With `CODE_SIGN_STYLE: Automatic` and a valid `DEVELOPMENT_TEAM`, Xcode selects the right identity per configuration on its own. Don't replace it with a per-configuration override unless automatic signing demonstrably fails — the whole point of automatic signing is that it picks correctly.

### Verify

```bash
cd Verso && ./generate-xcodeproj.sh
xcodebuild -project Verso.xcodeproj -showBuildSettings -target Verso \
  | grep -E "DEVELOPMENT_TEAM|CODE_SIGN"
```

Expect `DEVELOPMENT_TEAM` to print the 10-character Team ID from `Secrets.xcconfig`. Repeat with `-target ShareExtension` and `-target VersoTests` — all three must show it. An empty value here means the xcconfig isn't attached; re-check 1c/1d before moving on.

When reporting results back, confirm that the value is *present and identical across the three targets* rather than quoting it — it stays out of the transcript for the same reason it stays out of the repo.

## Task 2 — Remove the dead iCloud container declaration

### Decision (approved 2026-08-02)

`project.yml` declares an app-specific iCloud ubiquity container:

```yaml
NSUbiquitousContainers:
  iCloud.com.fabiosasseron.verso:
    NSUbiquitousContainerIsDocumentScopePublic: true
    NSUbiquitousContainerName: Verso
    NSUbiquitousContainerSupportedFolderLevels: Any
```

This key only takes effect if the app also holds the `com.apple.developer.icloud-container-identifiers` and `com.apple.developer.ubiquity-container-identifiers` entitlements. `Verso/Resources/Verso.entitlements` contains only the app group, so **the declaration is currently inert**. Confirmed: `grep` for `ubiquit`, `NSUbiquitous`, and `url(forUbiquityContainerIdentifier:)` across all Swift sources returns zero matches. No code depends on it.

**Decision: remove the key rather than add the entitlement.** Reasoning:

- Verso's storage model is a **user-selected folder** reached through the document picker and a security-scoped bookmark (`FolderBookmarkService`, `LibraryBookmarkResolver`). That path requires no iCloud entitlement whatsoever.
- An app-owned ubiquity container would introduce a *second*, parallel storage location alongside the user's chosen folder — two competing answers to "where do my articles live." That directly contradicts the file-first, no-lock-in positioning in `docs/PROJECT_STATUS.md`.
- The only gain is cosmetic: a "Verso" folder appearing by name in the Files app.
- It adds an iCloud capability to the App ID, which is additional App Review surface for a feature the app doesn't use.
- Reversible: adding the container later is cheap. Removing it *after* users have files inside it means a migration.

### Edits

**2a.** Delete the entire `NSUbiquitousContainers` block from `targets.Verso.info.properties` in `Verso/project.yml`.

**2b.** Regenerate. `Verso/Resources/Info.plist` is a generated artifact — confirm the key is gone from it after `./generate-xcodeproj.sh` rather than editing it by hand.

**2c.** Do **not** edit `docs/DONE.md`, which mentions the key. It's a historical archive of completed work; leave it accurate to what happened. Record the reversal in the commit message and in this plan.

### Verify

```bash
grep -rn "NSUbiquitous" Verso/ | grep -v Verso.xcodeproj
```

Expect no matches outside build artifacts.

## Task 3 — Add privacy manifests

Apple has required `PrivacyInfo.xcprivacy` for App Store submission since 2024. Two are needed: one for the app, one for the Share Extension. **An extension does not inherit its host app's manifest.**

### Audit before writing (do not skip)

The manifest must describe what the code *actually* does. A copied template that over- or under-declares is a rejection risk. From a grep pass on 2026-08-02:

| Required-reason API | Used? | Evidence |
|---|---|---|
| `NSPrivacyAccessedAPICategoryUserDefaults` | **Yes**, both targets | 8 files in `Verso/Sources/`; `Verso/Shared/LibraryBookmarkResolver.swift` is compiled into *both* targets |
| `NSPrivacyAccessedAPICategoryFileTimestamp` | **Yes**, app target | `MarkdownReader.swift:135-137` — `attributesOfItem(atPath:)` reading `.creationDate` |
| `NSPrivacyAccessedAPICategoryDiskSpace` | Verify | grep for `volumeAvailableCapacity`, `systemFreeSize` |
| `NSPrivacyAccessedAPICategorySystemBootTime` | Verify | grep for `systemUptime`, `mach_absolute_time` |
| `NSPrivacyAccessedAPICategoryActiveKeyboards` | Verify | grep for `activeInputModes` |

Re-run these greps yourself against `Verso/Sources/`, `Verso/Shared/`, and `Verso/ShareExtension/Sources/` — the table above is a starting point, not the answer. Scope the ShareExtension audit to *its own* source list (`ShareExtension/Sources`, `Generated`, `Shared`), which is much narrower than the app's.

Reason codes to use:

- UserDefaults → `CA92.1` (access to data stored only by the app itself and its app group)
- FileTimestamp → `C617.1` (timestamps of files provided to the app by the user) — correct here, since the files come from the user's selected folder. Do not use `DDA9.1` unless the timestamp is displayed in UI.

### Data collection

`AnalyticsService.swift` wraps TelemetryDeck, and there's an analytics-consent step in onboarding. Read `docs/ANALYTICS_STRATEGY.md` and `AnalyticsService.swift` before filling in `NSPrivacyCollectedDataTypes` — the declaration must match what is actually sent, and whether it is opt-in changes nothing about the requirement to declare it.

Expected shape (verify, don't assume): `NSPrivacyTracking` = `false`, `NSPrivacyTrackingDomains` = empty, and a `NSPrivacyCollectedDataTypeProductInteraction` entry marked not linked to identity and not used for tracking. The Share Extension almost certainly collects nothing — check whether `AnalyticsService` is in its source list before declaring anything for it.

Third-party SDK manifests are the vendors' responsibility, but confirm both ship one, since a missing signature on a listed SDK blocks upload:

```bash
find ~/Library/Developer/Xcode/DerivedData -name "PrivacyInfo.xcprivacy" -path "*TelemetryDeck*"
```

SwiftSoup is a pure parsing library and is not on Apple's commonly-used-SDK list.

### Edits

**3a.** Create `Verso/Resources/PrivacyInfo.xcprivacy`.
**3b.** Create `Verso/ShareExtension/Resources/PrivacyInfo.xcprivacy`.
**3c.** Confirm both are picked up as resources. `Verso/Resources` is already in the app target's `sources`, and XcodeGen classifies `.xcprivacy` as a resource — but the ShareExtension's `sources` list is `ShareExtension/Sources`, `Generated`, `Shared`, which does **not** include `ShareExtension/Resources`. You will likely need to add that path to the ShareExtension target's `sources` in `project.yml`. Verify in the generated project's Copy Bundle Resources phase; do not assume.

### Verify

After a build, the manifest must be at the bundle root of each product:

```bash
find ~/Library/Developer/Xcode/DerivedData -path "*Verso.app*" -name "PrivacyInfo.xcprivacy"
```

Expect two hits: one at `Verso.app/PrivacyInfo.xcprivacy`, one at `Verso.app/PlugIns/ShareExtension.appex/PrivacyInfo.xcprivacy`.

## Task 4 — Version parity between app and extension

`Verso/ShareExtension/Resources/Info.plist` hardcodes `CFBundleShortVersionString` `1.0` and `CFBundleVersion` `1`. The app's generated `Info.plist` currently carries the same values, so they match today — but they are maintained in two unrelated places and will drift on the first version bump. App Store Connect **rejects** uploads where an embedded extension's version doesn't match its host app.

Convert both to build settings so there is one source of truth: set `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` at the project level in `project.yml`, and reference them as `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)` in the ShareExtension's `Info.plist` and the app's `info.properties`.

Verify with `agvtool what-version` and `agvtool what-marketing-version`, then confirm the two built `Info.plist` files agree.
